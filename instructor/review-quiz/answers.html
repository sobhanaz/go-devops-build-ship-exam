    چرا پول int64 است و نه float64؟ (۴ نمره)

    float64 عدد را در مبنای ۲ (استاندارد IEEE-754) نگه می‌دارد. خیلی از کسرهای اعشاری ساده، مثل ۰٫۱، در مبنای ۲ نمایش دقیق ندارند (همان‌طور که ۱/۳ در مبنای ۱۰ دقیق نوشته نمی‌شود)، پس همیشه یک خطای گرد کردن کوچک همراهشان است:

    a, b := 0.1, 0.2
fmt.Println(a + b)        // 0.30000000000000004
fmt.Println(a+b == 0.3)   // false

    (نکته‌ی جالب: fmt.Println(0.1 + 0.2) با ثابت‌ها 0.3 چاپ می‌کند، چون Go ثابت‌ها را موقع کامپایل با دقت کامل حساب می‌کند. خطا وقتی ظاهر می‌شود که مقدارها در متغیر float64 باشند.)

    در یک دفتر کل این خطاها با هزاران تراکنش جمع می‌شوند، مقایسه‌ی balance >= amount ممکن است نتیجه‌ی غلط بدهد، و عددهای بزرگ‌تر از ۲۵۳ اصلاً دقیق نگه داشته نمی‌شوند. راه درست: پول را به کوچک‌ترین واحد (ریال) و به‌صورت عدد صحیح نگه داریم؛ جمع و تفریق int64 همیشه دقیق است.

    مزیت جانبی: وقتی فیلد amount از نوع int64 است، decode کردن 10.5 خودبه‌خود خطا می‌دهد و همان 400ی می‌شود که قرارداد خواسته.

    چرا طول owner با len() شمرده نمی‌شود؟ (۳ نمره)

    "سارا"۸۴معتبرمعتبر

    func NormalizeOwner(s string) (string, error) {
    s = strings.TrimSpace(s)
    n := utf8.RuneCountInString(s)
    if n < 2 || n > 40 {
        return "", ErrInvalidOwner
    }
    return s, nil   // پاسخ API نام تمیزشده را برمی‌گرداند
}
  3. ج

    چرا BIGINT و نه SERIAL/INTEGER؟ (۳ نمره)

    SERIAL در واقع یک INTEGER سی‌ودو بیتی است و حداکثر مقدارش 2,147,483,647 است، در حالی که در Go شناسه int64 است. وقتی 999999999999 به‌عنوان پارامتر $1 برای ستون INTEGER فرستاده می‌شود، pgx یا PostgreSQL خطای «خارج از محدوده» می‌دهد؛ این خطا هیچ‌کدام از خطاهای دامنه نیست، پس به 500 تبدیل می‌شود.

    با BIGINT (هم‌اندازه‌ی int64) کوئری اجرا می‌شود، هیچ ردیفی پیدا نمی‌شود، pgx.ErrNoRows به ErrAccountNotFound و بعد به 404 تبدیل می‌شود که جواب درست است.

    برای balance دلیل دیگری هم هست: سقف هر واریز یک میلیارد است، پس سه واریز کافی است تا موجودی از سقف INTEGER رد شود. قاعده‌ی کلی: نوع ستون در دیتابیس باید با نوع Go یکی باشد (int64 ↔ BIGINT).

چک‌لیست نمره (A)

  • float دودویی است و کسرهایی مثل ۰٫۱ را دقیق نشان نمی‌دهد؛ یک مثال درست (۰٫۱ + ۰٫۲) ۲
  • خطا جمع می‌شود و پول باید دقیق باشد؛ عدد صحیح در کوچک‌ترین واحد ۲
  • len بایت می‌شمارد و حرف فارسی ۲ بایت است؛ عددهای ۸/۴ و ۲/۱ ۲
  • نتیجه‌ی غلط: "س" با len قبول می‌شود؛ TrimSpace قبل از شمردن ۱
  • INTEGER سی‌ودو بیتی است (حدود ۲٫۱ میلیارد)، پس 500؛ با BIGINT نتیجه 404 است ۳

    چرا crypto/rand و نه math/rand؟ (۴ نمره)

    math/rand یک مولد شبه‌تصادفی است که برای سرعت و تکرارپذیری (شبیه‌سازی، تست) طراحی شده، نه برای غیرقابل‌پیش‌بینی بودن؛ مستندات خودش می‌گوید برای کارهای امنیتی استفاده نشود. در نسخه‌های قدیمی Go، seed پیش‌فرض ثابت بود و بعد از هر restart دقیقاً همان دنباله‌ی کدها ساخته می‌شد. با seed مثل time.Now().UnixNano() هم seed قابل حدس زدن است.

    خطر: لینک کوتاه معمولاً به چیزهای خصوصی اشاره می‌کند (سند اشتراکی، فاکتور، فرم). اگر کدها قابل پیش‌بینی باشند، مهاجم کدهای بعدی یا کدهای دیگران را حدس می‌زند و لینک‌های خصوصی را پیدا می‌کند (enumeration). crypto/rand از مولد امن سیستم‌عامل می‌خواند.

    const alphabet = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789"

func NewCode() (string, error) {
    b := make([]byte, 6)
    for i := range b {
        n, err := rand.Int(rand.Reader, big.NewInt(int64(len(alphabet))))
        if err != nil {
            return "", err
        }
        b[i] = alphabet[n.Int64()]
    }
    return string(b), nil
}

    فضای کدها ۶۲۶، یعنی حدود ۵۶٫۸ میلیارد حالت است. rand.Int برخلاف b % 62 ساده، توزیع یکنواخت و بدون سوگیری (bias) می‌دهد. (این نکته‌ی آخر امتیاز اضافه‌ی شفاهی است، نه الزامی.)

    چه بررسی‌هایی روی url لازم است؟ (۳ نمره)

    1. u, err := url.Parse(raw) و err == nil
    2. scheme فقط http یا https، بدون حساسیت به حروف: strings.EqualFold یا strings.ToLower
    3. u.Host != ""
    4. len(raw) <= 2048

    چرا javascript:؟ لینک کوتاه ظاهر قابل اعتمادی دارد. اگر آدرس جایی به‌صورت لینک نمایش داده شود (داشبورد، لیست لینک‌ها)، کلیک روی آن کد مهاجم را اجرا می‌کند (XSS). schemeهای دیگر مثل data:، file: و ftp: هم برای فیشینگ و open redirect سوءاستفاده می‌شوند. برای همین از لیست مجاز (فقط http/https) استفاده می‌کنیم، نه لیست ممنوع.

    تله: url.Parse("not a url") خطا نمی‌دهد! آن را یک مسیر نسبی می‌فهمد (Scheme=""، Host=""، Path="not a url"). url.Parse("http://") هم خطا نمی‌دهد ولی Host خالی است. javascript:alert(1) هم بدون خطا parse می‌شود (scheme javascript). پس فقط بررسی err بی‌فایده است و باید Scheme و Host را جدا بررسی کرد.

  3. ج

    302 در برابر 301، و کلمه‌های رزروشده (۳ نمره)

    301 Moved Permanently یعنی «دائمی». مرورگرها (و proxyها و CDNها) آن را cache می‌کنند، گاهی برای همیشه. از کلیک دوم به بعد، مرورگر مستقیم به مقصد می‌رود و درخواست اصلاً به سرور ما نمی‌رسد؛ پس کلیک شمرده نمی‌شود، و اگر لینک را حذف یا عوض کنیم، کاربرانی که cache دارند همچنان به مقصد قدیمی می‌روند. 302 Found موقت است و به‌طور پیش‌فرض cache نمی‌شود، پس هر کلیک به سرور می‌رسد و شمرده می‌شود.

    کلمه‌های رزروشده: در ServeMux نسخه‌ی ۱.۲۲، الگوی دقیق‌تر برنده است، پس GET /readyz بر GET /{code} اولویت دارد. readyz دقیقاً ۶ حرف از [A-Za-z0-9] است و مولد ممکن است آن را بسازد (احتمالش کم است، ولی صفر نیست). آن‌وقت لینک ساخته می‌شود ولی هرگز قابل دسترسی نیست و کاربر به‌جای ریدایرکت {"status":"ready"} می‌بیند؛ یک باگ بی‌صدا. پس اگر کد تولیدی تکراری یا رزروشده بود، دوباره بساز. کد دلخواه رزروشده (api، healthz، readyz، metrics، بدون حساسیت به حروف) جواب 400 می‌گیرد.

    سناریوی خرابی «اول بخوان، بعد بررسی کن، بعد بنویس» (۴ نمره)

    موجودی حساب ۱۰۰ است و دو درخواست برداشت ۸۰ هم‌زمان می‌رسند:

    زماندرخواست ۱ (برداشت ۸۰)درخواست ۲ (برداشت ۸۰)
    t1SELECT ← ۱۰۰
    t2SELECT ← ۱۰۰
    t3۱۰۰ ≥ ۸۰ ✓۱۰۰ ≥ ۸۰ ✓
    t4UPDATE … balance=20
    t5UPDATE … balance=20

    نتیجه: ۱۶۰ برداشت شده ولی موجودی ۲۰ است. جواب درست این بود که یکی 200 و دیگری 409 بگیرد. بانک ۸۰ ریال ضرر کرده. به این الگو race condition یا «بررسی و بعد اقدام» (check-then-act / TOCTOU) می‌گویند، و چون مقدار از Go نوشته می‌شود (balance=$1)، نوشتن یکی روی نوشتن دیگری می‌افتد (lost update). با واریزهای هم‌زمان هم همین اتفاق می‌افتد و مجموع کمتر می‌شود.

    ریشه‌ی مشکل: بررسی و نوشتن دو قدم جدا و بدون قفلاند و درخواست دیگری بینشان جا می‌شود. با دو رپلیکا، دو process جدا روی یک دیتابیس می‌نویسند، پس هیچ Mutexی در Go کمکی نمی‌کند.

  2. ب

    دو راه درست (۳ نمره)

    راه ۱ — UPDATE شرطی (یک دستور):

    UPDATE accounts SET balance = balance - $1
WHERE id = $2 AND balance >= $1
RETURNING id, owner, balance, created_at;

    PostgreSQL روی ردیف قفل می‌گیرد؛ UPDATE دوم صبر می‌کند تا اولی commit شود، بعد شرط WHERE را روی مقدار جدید دوباره بررسی می‌کند (۲۰ ≥ ۸۰ غلط است) و هیچ ردیفی تغییر نمی‌کند. ضمناً balance - $1 در خود دیتابیس و از مقدار فعلی حساب می‌شود، نه از مقدار کهنه‌ای که در Go خوانده شده. اگر ردیفی برنگشت، با SELECT EXISTS(SELECT 1 FROM accounts WHERE id=$1) تشخیص می‌دهیم: حساب نبود ← 404؛ بود ← 409.

    راه ۲ — SELECT … FOR UPDATE داخل تراکنش:

    BEGIN;
SELECT balance FROM accounts WHERE id = $1 FOR UPDATE;  -- قفل ردیف تا COMMIT
-- بررسی موجودی در Go: اگر کم بود ROLLBACK و 409
UPDATE accounts SET balance = balance - $2 WHERE id = $1;
INSERT INTO transactions (type, from_id, amount) VALUES ('withdraw', $1, $2);
COMMIT;

    FOR UPDATE ردیف را تا COMMIT یا ROLLBACK قفل می‌کند. SELECT … FOR UPDATE تراکنش دوم صبر می‌کند تا اولی تمام شود و بعد موجودی جدید (۲۰) را می‌بیند و 409 می‌دهد. نکته: FOR UPDATE فقط داخل تراکنش معنی دارد؛ بیرون از آن (autocommit) قفل بلافاصله آزاد می‌شود.

  3. ج

    چرا یک تراکنش SQL؟ و CHECK (balance >= 0)؟ (۳ نمره)

    انتقال سه نوشتن است. بدون تراکنش، اگر بعد از UPDATE اول خطا، crash، قطعی شبکه یا لغو context رخ دهد، پول نابود می‌شود (از مبدأ کم شده و به مقصد نرسیده)، یا ردیف تراکنش ثبت نمی‌شود و دفتر کل با موجودی‌ها جور درنمی‌آید. با BEGIN … COMMIT همه یا هیچ (atomicity): در هر خطا ROLLBACK همه چیز را برمی‌گرداند (pgx.BeginFunc این کار را خودکار می‌کند)، و بقیه هم حالت نیمه‌کاره را نمی‌بینند (isolation).

    CHECK (balance >= 0) آخرین خط دفاع در خود دیتابیس است (defense in depth). حتی اگر کد برنامه باگ داشته باشد یا کسی دستی SQL بزند، PostgreSQL نوشتنی را که موجودی را منفی کند با خطای 23514 (check_violation) رد می‌کند و تراکنش برمی‌گردد.

  • نام مشکل (race / lost update) و این‌که Mutex در Go با دو رپلیکا کمکی نمی‌کند ۲
  • UPDATE شرطی با AND balance >= $1 و تشخیص ۴۰۴/۴۰۹ با SELECT جدا ۲
  • FOR UPDATE داخل تراکنش و قفل ردیف تا COMMIT ۱
  • اتمیک بودن تراکنش و نقش CHECK ۳

    چرا HGET و بعد HSET کلیک گم می‌کند؟ (۴ نمره)

    زمانکلیک ۱کلیک ۲
    t1HGET clicks ← ۴۱
    t2HGET clicks ← ۴۱
    t3HSET clicks 42
    t4HSET clicks 42

    دو کلیک فقط یک واحد اضافه کردند. با ۱۰۰ کلیک هم‌زمان، خیلی از آن‌ها روی هم می‌افتند و نتیجه مثلاً ۶۳ می‌شود. هر دستور Redis به‌تنهایی اتمیک است، ولی دنباله‌ی دو دستور اتمیک نیست و درخواست دیگری بینشان جا می‌شود.

    درست: افزایش را به خود Redis بسپاریم. Redis دستورها را یکی‌یکی اجرا می‌کند و HINCRBY خواندن، جمع و نوشتن را در یک دستور انجام می‌دهد:

    s.rdb.HIncrBy(ctx, "link:"+code, "clicks", 1)

    یک sync.Mutex در Go این را حل نمی‌کند، چون با دو رپلیکا دو process جدا داریم.

  2. ب

    گرفتن اتمیک کد دلخواه (۳ نمره)

    با «اول EXISTS بعد HSET»، چند درخواست هم‌زمان همه EXISTS = 0 می‌بینند (هنوز کسی ننوشته)، همه می‌نویسند و همه 201 می‌گیرند. بدتر این‌که آخرین نوشتن، url قبلی را بی‌صدا عوض می‌کند، یعنی لینک کس دیگری ربوده می‌شود. باید بررسی و نوشتن یک قدم اتمیک باشند:

    • HSETNX link:{code} url <url>: فقط اگر فیلد وجود نداشته باشد می‌نویسد و true برمی‌گرداند؛ بقیه false می‌گیرند ← 409
    • SET key value NX، اگر طراحی کلیدها رشته‌ای باشد
    • یک اسکریپت Lua (مثل راه‌حل مرجع) که EXISTS، HSET و ZADD را یک‌جا انجام می‌دهد. Redis کل اسکریپت را اتمیک اجرا می‌کند و هیچ دستور دیگری وسطش اجرا نمی‌شود.

    با HSETNX، نوشتن بقیه‌ی فیلدها و ZADD دستورهای جدا هستند (پنجره‌ی کوچکی باقی می‌ماند)؛ Lua تمیزترین راه است.

  3. ج

    تله‌ی لینک زامبی (۳ نمره)

    HINCRBY روی کلیدی که وجود ندارد، آن را می‌سازد. پس کلیک روی لینک حذف‌شده یک hash نیمه‌کاره با {clicks: 1} و بدون url زنده می‌کند. بعد GET /api/links/{code} به‌جای 404، 200 با url خالی (یا 500) می‌دهد، و ممکن است ریدایرکت با Location خالی برگردد. تصحیح‌گر دقیقاً همین را امتحان می‌کند: حذف، کلیک، و بعد انتظار 404.

    «اول EXISTS بعد HINCRBY» با دو دستور جدا هم race دارد (حذف ممکن است بینشان بیفتد). راه حل تمیز اسکریپت Lua است، مثل راه‌حل مرجع:

    var hitScript = redis.NewScript(`

Mutex، رپلیکاها و بن‌بست

S1 · S7مشترک۱۰ نمره
  1. الف

    چرا sync.Mutex؟ (۳ نمره)

    سرور net/http هر درخواست را در goroutine جداگانه اجرا می‌کند، پس handlerها و store هم‌زمان صدا زده می‌شوند. map در Go برای نوشتن هم‌زمان امن نیست: runtime آن را تشخیص می‌دهد و کل برنامه را با fatal error: concurrent map writes می‌کشد. این یک panic معمولی نیست و recover() هم نمی‌تواند جلویش را بگیرد، پس middleware بازیابی کمکی نمی‌کند و سرور می‌میرد.

    حتی اگر crash نکند، acc.Balance += amount خواندن، جمع و نوشتن است و بدون قفل به‌روزرسانی‌ها گم می‌شوند (data race). Mutex بخش بحرانی را انحصاری می‌کند: در هر لحظه فقط یک goroutine داخلش است. go test -race این مشکل را پیدا می‌کند. (sync.RWMutex برای خواندن‌های هم‌زمان اختیاری است.)

  2. ب

    قفل تودرتو و الگوی درست (۳ نمره)

    sync.Mutex در Go بازگشتی (reentrant) نیست. اگر goroutine‌ای که قفل را دارد دوباره Lock بزند، برای همیشه منتظر خودش می‌ماند (deadlock). آن درخواست هرگز جواب نمی‌گیرد، و چون قفل هیچ‌وقت آزاد نمی‌شود، همه‌ی درخواست‌های بعدی هم پشت آن گیر می‌کنند و کل store یخ می‌زند.

    اگر برای حلش بین دو فراخوانی قفل را آزاد کنیم (Withdraw قفل/باز، بعد Deposit قفل/باز)، عمل اتمیک نیست:

    • در فاصله‌ی دو قدم، بقیه پولی را می‌بینند که از مبدأ رفته و به مقصد نرسیده (مجموع موجودی‌ها موقتاً غلط است).
    • اگر Deposit شکست بخورد (مقصد وجود ندارد)، پول از مبدأ کم شده و گم می‌شود.
    • ترتیب خطا هم خراب می‌شود: Withdraw ممکن است 409 بدهد در حالی که مقصد وجود ندارد و جواب درست 404 است.

    الگوی درست: یک بار در ابتدای تابع قفل بگیر و همه کار را زیر همان قفل انجام بده (یا تابع‌های کمکی مثل withdrawLocked بنویس که فرض می‌کنند قفل گرفته شده):

    func (m *Memory) Transfer(ctx context.Context, from, to, amount int64) (bank.Transaction, error) {
    m.mu.Lock()
    defer m.mu.Unlock()

    src, ok1 := m.accounts[from]
    dst, ok2 := m.accounts[to]
    if !ok1 || !ok2 {
        return bank.Transaction{}, bank.ErrAccountNotFound   // 404 قبل از 409
    }
    if src.Balance < amount {
        return bank.Transaction{}, bank.ErrInsufficientFunds
    }
    src.Balance -= amount
    dst.Balance += amount
    // ثبت ردیف تراکنش با id بعدی، هنوز زیر همان قفل
    ...
}

    در B هم همین است: Hit باید بررسی وجود لینک و افزایش کلیک را زیر یک قفل انجام دهد.

  3. ج

    STORE=memory با دو رپلیکا (۲ نمره)

    هر pod یک process جدا با حافظه‌ی خودش است. Service درخواست‌ها را بین podها پخش می‌کند. حسابی (یا لینکی) که روی pod اول ساخته شده، وقتی درخواست بعدی به pod دوم برسد 404 می‌گیرد؛ واریزها بین دو نسخه تقسیم می‌شوند و موجودی‌ها (یا کلیک‌ها) از هم جدا می‌شوند. برای چند رپلیکا، state باید در یک datastore مشترک بیرونی باشد.

    چرا امتیاز هم‌روندی فقط روی datastore واقعی؟ Mutex فقط داخل یک process محافظت می‌کند. store درون‌حافظه‌ای با یک Mutex تست هم‌روندی را بی‌زحمت پاس می‌کند، ولی این چیزی درباره‌ی درستی برنامه در production نمی‌گوید. port-forward هم فقط به یک pod وصل می‌شود، پس تصحیح‌گر نمی‌تواند حالت memory با دو رپلیکا را از روی API تشخیص دهد؛ برای همین مدرس STORE را در ConfigMap بررسی کرد.

  4. د

    بن‌بست 40P01 (۲ نمره)

    تراکنش T1 (P→Q) ردیف P را قفل می‌کند و منتظر Q می‌ماند؛ هم‌زمان T2 (Q→P) ردیف Q را قفل کرده و منتظر P است. هر کدام منتظر دیگری‌اند و این انتظار هیچ‌وقت تمام نمی‌شود. آشکارساز بن‌بست PostgreSQL (بعد از deadlock_timeout، پیش‌فرض ۱ ثانیه) یکی را با SQLSTATE 40P01 لغو می‌کند و کاربر 500 می‌بیند. پول حفظ می‌شود ولی شرط B4 (همه 201) شکست می‌خورد.

    راه حل: ترتیب قفل کردن را برای همه یکسان کن: همیشه اول id کوچک‌تر، بعد بزرگ‌تر. آن‌وقت تراکنش دوم فقط صبر می‌کند تا اولی commit شود. به‌عنوان تور ایمنی، تراکنش را در صورت 40P01 یا 40001 چند بار با فاصله‌ی کوتاه دوباره اجرا کن. (روش UPDATE شرطی هم همین مشکل را دارد اگر به ترتیب from→to قفل بگیرد.)

for _, id := range []int64{min(from, to), max(from, to)} {
    err := tx.QueryRow(ctx,
        `SELECT balance FROM accounts WHERE id = $1 FOR UPDATE`, id).Scan(&balance)
    ...
}
// و retryOnConflict: اگر کد خطا 40P01 یا 40001 بود، تا ۳ بار دوباره

چک‌لیست نمره

  • goroutine جدا برای هر درخواست؛ concurrent map writes برنامه را می‌کشد و recover نمی‌شود ۲
  • lost update روی موجودی/کلیک؛ -race ۱
  • Mutex بازگشتی نیست، پس deadlock و یخ زدن کل store ۱
  • آزاد کردن قفل بین دو قدم، اتمیک بودن را از بین می‌برد؛ الگوی «یک بار قفل» ۲
  • هر pod حافظه‌ی خودش را دارد و Service پخش می‌کند؛ Mutex فقط داخل یک process کار می‌کند ۲
  • قفل متقاطع، 40P01، و ترتیب ثابت قفل (min/max) + retry ۲

    sentinel error، errors.Is و تابع واحد (۳ نمره)

    خطای ثابت یک متغیر سطح پکیج با هویت ثابت است که بقیه‌ی کد با آن مقایسه می‌کند:

    ErrAccountNotFound   = errors.New("account not found")
    ErrInsufficientFunds = errors.New("insufficient funds")
)

    لایه‌های پایین‌تر معمولاً خطا را با توضیح بیشتر می‌پیچند: fmt.Errorf("transfer %d→%d: %w", from, to, bank.ErrAccountNotFound). حالا err == bank.ErrAccountNotFound غلط است، چون فقط لایه‌ی بیرونی را مقایسه می‌کند. errors.Is زنجیره‌ی Unwrap را دنبال می‌کند و درست تشخیص می‌دهد.

    یک تابع واحد (مثل statusFor در راه‌حل مرجع) یعنی:

    • یکدستی: یک خطا در همه‌ی handlerها همیشه یک status می‌گیرد.
    • تغییر در یک جا انجام می‌شود.
    • هر خطای ناشناخته 500 با پیام کلی "internal error" می‌گیرد و جزئیات داخلی (متن خطای SQL) به کاربر لو نمی‌رود.
    • پکیج دامنه (bank یا link) هیچ وابستگی‌ای به HTTP ندارد.
    func statusFor(err error) int {
    switch {
    case errors.Is(err, bank.ErrInvalidAmount), errors.Is(err, bank.ErrSameAccount) /* ... */:
        return http.StatusBadRequest           // 400
    case errors.Is(err, bank.ErrAccountNotFound):
        return http.StatusNotFound             // 404
    case errors.Is(err, bank.ErrInsufficientFunds):
        return http.StatusConflict             // 409
    default:
        return http.StatusInternalServerError  // 500
    }
}

    -race (۲ نمره)

    کامپایلر هر دسترسی به حافظه را instrument می‌کند و در زمان اجرا، اگر دو goroutine بدون همگام‌سازی به یک خانه‌ی حافظه دسترسی داشته باشند و دست‌کم یکی بنویسد، WARNING: DATA RACE را با stack هر دو طرف چاپ می‌کند و تست شکست می‌خورد.

    محدودیت‌ها: فقط raceهایی را می‌بیند که در همان اجرا واقعاً رخ داده‌اند (پویاست، نه اثبات)؛ race منطقی در دیتابیس (مثل SELECT و بعد UPDATE از دو process) و deadlock را نمی‌بیند؛ و برنامه را چند برابر کندتر می‌کند.

    در Linux، ابزار race به cgo و کامپایلر C نیاز دارد. اگر gcc نصب نباشد، Go خودکار CGO_ENABLED=0 می‌گذارد و خطای -race requires cgo می‌آید. راه حل: sudo apt install -y build-essential و بررسی با go env CGO_ENABLED (باید 1 باشد). در macOS کامپایلر Xcode کافی است.

    CI دیتابیس ندارد؛ تستی که به دیتابیس وصل شود CI را قرمز می‌کند. تست باید سریع، قطعی و همه‌جا قابل اجرا باشد. اینترفیس Store و پیاده‌سازی memory همین را ممکن می‌کنند: handlerها را با store درون‌حافظه‌ای تست می‌کنیم (تزریق وابستگی). تست یکپارچه را اختیاری می‌کنیم:

    url := os.Getenv("MINIBANK_TEST_DATABASE_URL")
if url == "" {

}

req := httptest.NewRequest("GET", "/accounts/999999999999", nil)
rec := httptest.NewRecorder()
srv.ServeHTTP(rec, req)
if rec.Code != http.StatusNotFound { t.Fatalf("got %d", rec.Code) }

لینوکس و اسکریپت Bash

S3مشترک۱۰ نمره
  1. الف

    shebang و set -euo pipefail (۳ نمره)

    • #!/usr/bin/env bash: کرنل از خط اول می‌فهمد اسکریپت را با چه مفسری اجرا کند. env، bash را در PATH پیدا می‌کند؛ قابل‌حمل‌تر از /bin/bash است (مثلاً bash نصب‌شده با Homebrew در macOS یا سیستم‌هایی که /bin/bash ندارند). بدون shebang ممکن است اسکریپت با sh اجرا شود که pipefail و [[ ]] ندارد.
    • -e: اگر دستوری کد خروج غیرصفر بدهد، اسکریپت همان‌جا متوقف می‌شود (به‌جای ادامه دادن با حالت خراب). استثنا: دستورهای داخل شرط if و زنجیره‌های && و ||.
    • -u: استفاده از متغیر تعریف‌نشده خطاست. غلط تایپی مثل $BSAE به‌جای رشته‌ی خالی، اسکریپت را متوقف می‌کند.
    • -o pipefail: کد خروج یک pipeline برابر کد آخرین دستور شکست‌خورده است، نه فقط دستور آخر. بدون آن، در curl … | jq … شکست curl پنهان می‌ماند.

    بیت اجرایی هم باید با chmod +x ثبت شود تا Git فایل را با mode 100755 ذخیره کند (در ویندوز: git update-index --chmod=+x scripts/*.sh).

  2. ب

    دو باگ smoke.sh (۴ نمره)

    باگ ۱ — curl با set -e: وقتی سرور خاموش است، curl با کد ۷ (couldn't connect) خارج می‌شود. -w همچنان 000 چاپ می‌کند، ولی کد خروج انتساب code=$(…) همان کد خروج curl است، یعنی ۷. set -e اسکریپت را همان‌جا می‌کشد، پس هیچ خط FAIL و هیچ جمع‌بندی‌ای چاپ نمی‌شود. راه حل: || code=000 (و --max-time 5 تا روی سرور گیرکرده تا ابد منتظر نماند).

    باگ ۲ — ((passed++)): افزایش پسوندی مقدار قبلی را برمی‌گرداند. وقتی passed صفر است، حاصل عبارت ۰ است و (( )) برای حاصل صفر کد خروج ۱ می‌دهد؛ در Bash 4.1 به بعد (لینوکس، WSL، runnerهای CI) set -e اسکریپت را بعد از اولین PASS می‌کشد. نکته‌ی جالب: bash پیش‌فرض macOS نسخه‌ی ۳٫۲ است و آنجا اسکریپت زنده می‌ماند، پس «روی Mac من کار می‌کند ولی در لینوکس نه». راه حل: passed=$((passed + 1)).

    #!/usr/bin/env bash
set -euo pipefail
BASE=${1:-http://localhost:8080}
passed=0; failed=0

check() {  # check NAME EXPECTED METHOD PATH [BODY]
  local name=$1 want=$2 method=$3 path=$4 body=${5:-}
  local code
  code=$(curl -s -o /tmp/body.json -w '%{http_code}' --max-time 5 \
    -X "$method" "$BASE$path" ${body:+-d "$body"}) || code=000
  if [ "$code" = "$want" ]; then
    echo "PASS $name"; passed=$((passed + 1))
  else
    echo "FAIL $name (expected $want, got $code)"; failed=$((failed + 1))
  fi
}

check healthz 200 GET /healthz
check readyz  200 GET /readyz
# ... بقیه‌ی بررسی‌ها

echo "$passed passed, $failed failed"
[ "$failed" -eq 0 ]   # کد خروج اسکریپت

    (چرا local code جدا از انتساب؟ چون local code=$(…) کد خروج local را برمی‌گرداند که همیشه ۰ است و شکست curl را پنهان می‌کند.)

  3. ج

    id ثابت، استخراج از JSON و کد خروج (۳ نمره)

    شناسه‌ها را سرور تعیین می‌کند، صعودی‌اند و دوباره استفاده نمی‌شوند. دیتابیس ممکن است داده‌ی قبلی داشته باشد (volume ماندگار، داده‌ی تصحیح‌گر، اجرای قبلی smoke). id=1 ممکن است مال حساب دیگری باشد یا اصلاً نباشد. smoke باید روی دیتابیس تازه و پر، و روی Compose و Kubernetes، همیشه درست کار کند. تنها استثنا id خیلی بزرگ مثل 999999999999 برای «حساب ناموجود» است.

    # با jq
id=$(jq -r '.id // empty' /tmp/body.json 2>/dev/null || true)
# بدون jq
id=$(grep -o '"id":[0-9]*' /tmp/body.json 2>/dev/null | cut -d: -f2 || true)
# B: کد لینک
code=$(grep -o '"code":"[^"]*"' /tmp/body.json | cut -d'"' -f4 || true)

    کد خروج: ماشین‌ها (CI، اسکریپت‌های دیگر، تصحیح‌گر) به کد خروج نگاه می‌کنند، نه به متن. مرحله‌ی CI فقط با کد غیرصفر قرمز می‌شود، و scripts/smoke.sh && echo deployed فقط با کد ۰ ادامه می‌دهد.

چک‌لیست نمره

  • shebang با env و دلیلش ۱
  • معنی درست هر سه گزینه‌ی -e، -u، pipefail ۲
  • باگ curl: کد خروج ۷ و set -e؛ راه حل || code=000 ۲
  • باگ ((passed++)) با مقدار صفر؛ راه حل $((passed + 1)) ۲
  • دلیل نداشتن id ثابت و یک روش استخراج ۲
  • کد خروج غیرصفر برای CI و اتوماسیون ۱

سؤال تکمیلی

Docker

S4مشترک۱۰ نمره
  1. الف

    مشکل‌های Dockerfile (۴ نمره؛ هر ۵ مورد درست = نمره‌ی کامل)

    1. ایمیج نهایی همان golang است: کل toolchain (بیش از ۸۰۰ مگابایت) داخل ایمیج می‌ماند؛ قرارداد حداکثر ۳۰ مگابایت است. سطح حمله هم بزرگ است (کامپایلر، shell، مدیر بسته).
    2. تگ latest: تکرارپذیر نیست؛ امروز ۱٫۲۶ است و فردا ۱٫۲۷. باید نسخه را ثابت کرد (golang:1.26-alpine) و دست‌کم برابر خط go در go.mod باشد.
    3. کامنت انتهای خط: COPY . . # copy the source code. در Dockerfile، # فقط در ابتدای خط کامنت است؛ اینجا #، copy، the و … جزو آرگومان‌های COPY حساب می‌شوند و build با خطای «فایل پیدا نشد» متوقف می‌شود.
    4. ترتیب cache: COPY . . قبل از go mod download است، پس با هر تغییر در یک فایل .go لایه باطل می‌شود و همه‌ی ماژول‌ها دوباره دانلود می‌شوند. درست: اول COPY go.mod go.sum ./، بعد RUN go mod download، بعد COPY . ..
    5. اجرا با root: USER ندارد. اگر برنامه نفوذپذیر باشد، مهاجم داخل کانتینر root است و فرار از کانتینر آسان‌تر می‌شود.
    6. نبود .dockerignore: .git، باینری‌ها و مهم‌تر از همه .env (رمزها!) وارد build context و لایه‌های ایمیج می‌شوند؛ build کندتر و cache بی‌دلیل باطل می‌شود.
    7. CMD به شکل shell: CMD ./minibank با /bin/sh -c اجرا می‌شود. در scratch اصلاً /bin/sh وجود ندارد و کانتینر بالا نمی‌آید؛ و اگر shell فرایند اصلی (PID 1) باشد، ممکن است SIGTERM به برنامه نرسد و خاموشی مرتب کار نکند. قرارداد شکل exec می‌خواست: ENTRYPOINT ["/minibank"].
    8. باینری استاتیک نیست: بدون CGO_ENABLED=0 و -ldflags "-s -w"، باینری بزرگ‌تر است و ممکن است به libc وابسته باشد.
  2. ب

    نسخه‌ی درست (۳ نمره) — همان راه‌حل مرجع (۱۳٫۲ مگابایت)

    # ---- مرحله‌ی ساخت ----
FROM golang:1.26-alpine AS build
WORKDIR /src
# اول وابستگی‌ها: این لایه تا وقتی go.mod/go.sum عوض نشوند cache می‌ماند
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" \
    -o /out/minibank ./cmd/minibank

# ---- مرحله‌ی نهایی: ایمیج خالی + باینری ----
FROM scratch
COPY --from=build /out/minibank /minibank
USER 65532:65532
EXPOSE 8080
HEALTHCHECK --interval=10s --timeout=3s CMD ["/minibank", "-healthcheck"]
ENTRYPOINT ["/minibank"]

    به‌همراه .dockerignore: .git، .env، /minibank، k8s/، *.out، coverage*. (HEALTHCHECK اختیاری است.)

  3. ج

    چهار «چرا» (۳ نمره)

    • CGO_ENABLED=0: باینری کاملاً Go و استاتیک ساخته می‌شود و به کتابخانه‌ی C سیستم (glibc یا musl) و dynamic loader نیاز ندارد. scratch هیچ libcی ندارد؛ باینری دینامیک آنجا با خطای گیج‌کننده‌ی no such file or directory اجرا نمی‌شود (چون loader پیدا نمی‌شود، نه خود فایل). پکیج net به‌طور پیش‌فرض ممکن است از cgo برای DNS استفاده کند؛ با این فلگ resolver خالص Go استفاده می‌شود.
    • -ldflags "-s -w": -s جدول نمادها و -w اطلاعات دیباگ DWARF را حذف می‌کند؛ باینری حدود ۳۰٪ کوچک‌تر می‌شود. stack trace مربوط به panic همچنان نام تابع‌ها را دارد، فقط دیباگر کمتر اطلاعات دارد.
    • USER 65532:65532 عددی: scratch فایل /etc/passwd ندارد، پس نام کاربری مثل USER nonroot قابل تبدیل به uid نیست و کانتینر اجرا نمی‌شود. uid:gid عددی بدون passwd کار می‌کند. ۶۵۵۳۲ همان کاربر قراردادی nonroot در distroless است، و runAsNonRoot: true در Kubernetes برای بررسی به uid عددی نیاز دارد.
    • HEALTHCHECK بدون curl: scratch هیچ چیز ندارد: نه shell، نه curl، نه wget. پس HEALTHCHECK CMD curl … همیشه شکست می‌خورد و کانتینر unhealthy می‌شود. راه حل: یک فلگ در خود باینری (-healthcheck) که یک GET به localhost:8080/healthz بزند و با کد ۰ یا ۱ خارج شود. به همین دلیل docker exec … sh هم کار نمی‌کند و دیباگ با لاگ یا kubectl debug انجام می‌شود.

چک‌لیست نمره

  • هر مشکل درست از فهرست بالا ۰٫۸ نمره، حداکثر ۴ ۴
  • Dockerfile درست: دو مرحله، ترتیب cache، CGO_ENABLED=0، scratch، USER، ENTRYPOINT به شکل exec ۳
  • توضیح درست دست‌کم سه مورد از چهار «چرا» ۳

سؤال تکمیلی

Docker Compose

S5مشترک۱۰ نمره
  1. الف

    depends_on با و بدون شرط (۳ نمره)

    depends_on: [db] فقط صبر می‌کند تا کانتینر دیتابیس شروع شود (process اجرا شده باشد)، نه تا وقتی که آماده‌ی پذیرفتن اتصال است. PostgreSQL چند ثانیه (و بار اول به‌خاطر initdb بیشتر) وقت لازم دارد. برنامه زودتر وصل می‌شود، connection refused می‌گیرد، crash می‌کند و مدام restart می‌شود. با condition: service_healthy، Compose صبر می‌کند تا healthcheck دیتابیس سبز شود:

    services:
  db:
    image: postgres:16-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 10
  app:
    depends_on:
      db:
        condition: service_healthy

# B (Redis با رمز):
#   test: ["CMD-SHELL", "redis-cli --no-auth-warning -a \"$$REDIS_PASSWORD\" ping | grep -q PONG"]

    $$ یعنی Compose متغیر را جایگزین نکند و خود shell داخل کانتینر آن را بخواند. یادت باشد این شرط فقط موقع شروع است؛ اگر دیتابیس بعداً restart شود، برنامه باید خودش کنار بیاید (برای همین /readyz داریم).

  2. ب

    چرا db و نه localhost؟ (۲ نمره)

    هر کانتینر network namespace خودش را دارد. localhost داخل کانتینر برنامه یعنی خود همان کانتینر، نه دیتابیس، پس آنجا هیچ‌کس روی ۵۴۳۲ گوش نمی‌دهد. Compose یک شبکه‌ی مشترک با DNS داخلی می‌سازد و نام سرویس (db یا redis) به IP همان کانتینر ترجمه می‌شود. پورت هم پورت داخل کانتینر است، نه پورت host. در Kubernetes هم همین الگو با نام Service (postgres، redis) تکرار می‌شود.

  3. ج

    ماندگاری داده و منتشر نکردن پورت (۳ نمره)

    با named volume (pgdata:/var/lib/postgresql/data؛ در B redis-data:/data به‌همراه --appendonly yes)، داده جدا از چرخه‌ی عمر کانتینر نگه داشته می‌شود:

    • docker compose down کانتینرها و شبکه را حذف می‌کند ولی volumeهای نام‌دار را نه، پس بعد از up داده هست.
    • docker compose down -v volumeها را هم پاک می‌کند و داده از بین می‌رود.
    • بدون volume، داده در لایه‌ی قابل‌نوشتن کانتینر است و با حذف کانتینر می‌رود.

    منتشر نکردن پورت: فقط برنامه به دیتابیس نیاز دارد و از شبکه‌ی داخلی Compose به آن می‌رسد. اگر 5432:5432 منتشر شود، دیتابیس روی host (و شاید روی کل شبکه‌ی محلی؛ Docker قوانین فایروال‌هایی مثل ufw را دور می‌زند) باز است و هدف brute force می‌شود. Redis باز روی اینترنت یکی از رایج‌ترین راه‌های نفوذ است. اصل کمترین دسترسی، به‌علاوه‌ی جلوگیری از تداخل با Postgres محلی روی همان پورت.

  4. د

    .env، .env.example و restart (۲ نمره)

    .env مقدارهای واقعی (رمزها) را دارد، در .gitignore است و هرگز کامیت نمی‌شود. .env.example الگوی همان فایل با مقدارهای نمونه است و کامیت می‌شود تا هر کسی بداند چه متغیرهایی لازم است (cp .env.example .env). Compose فایل .env را خودکار برای جایگزینی ${POSTGRES_PASSWORD} می‌خواند. هیچ رمزی داخل کد Go یا compose.yaml نوشته نمی‌شود.

    restart: unless-stopped: اگر کانتینر crash کند یا Docker daemon (یا سیستم) restart شود، Docker آن را دوباره بالا می‌آورد، مگر این‌که خودمان دستی متوقفش کرده باشیم (docker compose stop).

چک‌لیست نمره

  • «شروع شده» در برابر «آماده»؛ healthcheck درست برای نسخه‌ی خودش ۳
  • localhost یعنی خود کانتینر؛ DNS سرویس در شبکه‌ی Compose ۲
  • down volume را نگه می‌دارد و down -v پاک می‌کند ۲

  • نقش .env / .env.example و restart policy ۲

    • needs: test: jobها به‌طور پیش‌فرض موازی اجرا می‌شوند. با needs، build فقط وقتی اجرا می‌شود که test سبز شده باشد؛ وگرنه ممکن است ایمیجی از کد خراب ساخته شود.
    • test -z "$(gofmt -l .)": gofmt -l فهرست فایل‌هایی را که فرمت نشده‌اند چاپ می‌کند (و خودش همیشه کد ۰ می‌دهد). $(…) این فهرست را می‌گیرد و test -z فقط وقتی کد ۰ می‌دهد که رشته خالی باشد. اگر فایلی فرمت نشده باشد، کد ۱ و مرحله قرمز می‌شود.
    • چرا gofmt -w . اشتباه است؟ فایل‌ها را روی ماشین موقت CI بازنویسی می‌کند و همیشه کد ۰ می‌دهد؛ هیچ‌وقت شکست نمی‌خورد و اصلاحش هم کامیت نمی‌شود. CI برای بررسی است، نه اصلاح.
  2. ب

    چرا CI به دیتابیس نیاز نداشت؟ (۲ نمره)

    چون تست‌ها با store درون‌حافظه‌ای (از طریق اینترفیس Store) نوشته شده‌اند و تست یکپارچه وقتی env مخصوصش نباشد t.Skip می‌شود. اگر تستی مستقیم به localhost:5432 وصل شود، در runner گیت‌هاب کسی روی آن پورت گوش نمی‌دهد، connection refused می‌گیرد و CI قرمز می‌شود. (راه‌حل مرجع یک job جدای integration با services: postgres دارد، ولی این پیشرفته و اختیاری بود.)

  3. ج

    fast-forward و --no-ff (۳ نمره)

    اگر از وقتی شاخه ساخته شده، main کامیت جدیدی نگرفته باشد، Git موقع merge فقط اشاره‌گر main را جلو می‌برد تا به نوک شاخه برسد (fast-forward). هیچ کامیت mergeی ساخته نمی‌شود و تاریخچه طوری خطی می‌شود که انگار همه چیز مستقیم روی main کامیت شده؛ مرز مرحله‌ها گم می‌شود. در جریان این آزمون (یک نفر، شاخه‌های پشت سر هم) تقریباً همیشه همین اتفاق می‌افتاد.

    git merge --no-ff همیشه یک کامیت merge با دو والد می‌سازد؛ در git log --graph هر مرحله یک شاخه‌ی جدا دیده می‌شود و مدرس می‌تواند دست‌کم ۴ merge را بشمارد.

    *   merge: build/docker
|\
| * build: multi-stage dockerfile
|/
*   merge: chore/scripts
|\
| * chore: env check and smoke test scripts
|/

    در GitHub: Squash and merge همه‌ی کامیت‌های شاخه را در یک کامیت معمولی روی main فشرده می‌کند (کامیت merge ندارد و کامیت‌های تکی هم گم می‌شوند، که به معیار «۱۰ کامیت معنادار» هم آسیب می‌زند). Rebase and merge کامیت‌ها را خطی روی main دوباره می‌سازد (باز هم بدون کامیت merge). فقط Create a merge commit معادل --no-ff است.

  4. د

    تله‌ی .gitignore (۲ نمره)

    الگوی بدون / مثل minibank با هر فایل یا پوشهای به این نام در هر عمقی جور می‌شود. پس پوشه‌ی cmd/minibank/ هم نادیده گرفته می‌شود و cmd/minibank/main.go هرگز کامیت نمی‌شود. روی لپ‌تاپ خودت همه چیز کار می‌کند چون فایل روی دیسک هست؛ ولی در CI، در clone تمیز و در docker build (که از context همان ریپو می‌سازد، یا از clone مدرس) خطای «پکیج پیدا نشد» می‌آید. این یعنی «روی سیستم من کار می‌کند».

    /minibank با / در ابتدا فقط به ریشه‌ی ریپازیتوری می‌چسبد، یعنی فقط باینری. راه دیگر: خروجی build را در bin/ بگذار و bin/ را ignore کن. بررسی: git check-ignore -v cmd/minibank/main.go.

Kubernetes: بررسی سلامت، خاموشی مرتب و عیب‌یابی

S7 · D3مشترک۱۰ نمره
  1. الف

    سه probe (۳ نمره)

    probeچه می‌پرسداگر شکست بخورد
    startupProbe«شروع برنامه تمام شده؟»تا وقتی شکست می‌خورد، liveness و readiness اجرا نمی‌شوند. اگر از failureThreshold × periodSeconds (مثلاً ۳۰×۲ = ۶۰ ثانیه) بیشتر شود، کانتینر kill و restart می‌شود.
    livenessProbe«process زنده است و گیر نکرده؟»kubelet کانتینر را kill و restart می‌کند (RESTARTS بالا می‌رود؛ تکرارش یعنی CrashLoopBackOff).
    readinessProbe«الان می‌تواند ترافیک بگیرد؟»pod از endpointهای Service خارج می‌شود و ترافیک نمی‌گیرد، ولی restart نمی‌شود؛ با سبز شدن دوباره برمی‌گردد.

    چرا liveness روی /readyz نه؟ /readyz به دیتابیس وابسته است. اگر دیتابیس قطع شود، liveness همهی podهای سالم برنامه شکست می‌خورد و Kubernetes همه را هم‌زمان و پشت سر هم restart می‌کند تا به CrashLoopBackOff برسند. restart هیچ کمکی به دیتابیس نمی‌کند (یک خرابی آبشاری)، و وقتی دیتابیس برمی‌گردد، podها در تأخیر back-off (تا ۵ دقیقه) گیر کرده‌اند و بازگشت کندتر می‌شود. liveness فقط باید خود process را بسنجد: /healthz که هرگز به دیتابیس دست نمی‌زند.

    startupProbe در راه‌حل مرجع برای این است که برنامه قبل از گوش دادن به HTTP منتظر Postgres می‌ماند؛ در اولین kubectl apply، Postgres ممکن است ۳۰ تا ۶۰ ثانیه طول بکشد و بدون startupProbe، liveness برنامه را زودتر می‌کشد.

  2. ب

    قطع دیتابیس و timeoutSeconds: 3 (۲ نمره)

    • /readyz دیتابیس را ping می‌کند، ping (با timeout دو ثانیه) شکست می‌خورد و جواب 503 و {"status":"not ready"} است.
    • بعد از failureThreshold بار (مثلاً ۲×۵ ثانیه)، podهای برنامه 0/1 READY می‌شوند و از endpointهای Service خارج می‌شوند (kubectl get endpoints خالی می‌شود)؛ درخواست‌ها به pod نیمه‌خراب نمی‌رسند.
    • /healthz همچنان 200 است، liveness سالم است و هیچ restartی رخ نمی‌دهد (RESTARTS صفر می‌ماند).
    • وقتی دیتابیس برمی‌گردد، ping موفق می‌شود و podها خودکار Ready و به Service برمی‌گردند؛ بدون دخالت ما.

    timeoutSeconds: 3: timeout پیش‌فرض probe یک ثانیه است، ولی /readyz ممکن است تا ۲ ثانیه منتظر ping بماند. با timeout یک ثانیه، kubelet قبل از این‌که برنامه حتی جواب بدهد تسلیم می‌شود و با کمی کندی شبکه، readiness بی‌دلیل قطع و وصل می‌شود (flapping). قاعده: timeout probe باید از timeout داخلی برنامه بیشتر باشد.

  3. ج

    توقف pod و خاموشی مرتب (۲ نمره)

    1. pod وضعیت Terminating می‌گیرد و هم‌زمان از endpointهای Service خارج می‌شود تا درخواست جدید نگیرد.
    2. kubelet به PID 1 کانتینر SIGTERM می‌فرستد. (به لطف ENTRYPOINT به شکل exec، PID 1 خود باینری ماست، نه shell.)
    3. برنامه با signal.NotifyContext سیگنال را می‌گیرد، لاگ می‌نویسد و srv.Shutdown(ctx) را با timeout ده ثانیه صدا می‌زند: اتصال جدید نمی‌پذیرد و صبر می‌کند تا درخواست‌های در حال اجرا تمام شوند. بعد store.Close() اتصال دیتابیس را می‌بندد، پیام پایانی را لاگ می‌کند و با کد ۰ خارج می‌شود.
    4. اگر process بعد از terminationGracePeriodSeconds (پیش‌فرض ۳۰ ثانیه) هنوز زنده باشد، kubelet SIGKILL می‌فرستد (قطع ناگهانی، بدون تمیزکاری).

    چون ۱۰ ثانیه کمتر از ۳۰ ثانیه است، برنامه همیشه قبل از SIGKILL مرتب خارج می‌شود. اگر برنامه SIGTERM را نادیده بگیرد (مثلاً shell به‌عنوان PID 1)، Kubernetes ۳۰ ثانیه صبر می‌کند و بعد می‌کشد: rolloutهای کند و درخواست‌های نیمه‌کاره.

    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
go func() { _ = srv.ListenAndServe() }()

<-ctx.Done()                                      // SIGTERM یا Ctrl+C
logger.Info("shutdown signal received, draining requests")
shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
_ = srv.Shutdown(shutdownCtx)                     // تمام کردن درخواست‌های در حال اجرا
st.Close()                                        // بستن اتصال datastore
logger.Info("bye")

    سه سناریوی عیب‌یابی (۳ نمره، هر کدام ۱)

    (۱) latest و ImagePullBackOff: وقتی تگ latest است (یا تگی نیست)، پیش‌فرض imagePullPolicy برابر Always است و kubelet هر بار سعی می‌کند ایمیج را از Docker Hub بکشد. ایمیج ما فقط محلی ساخته شده و با kind load داخل نود رفته، روی Docker Hub نیست (یا Docker Hub مسدود است)، پس ErrImagePull و بعد ImagePullBackOff. راه حل: تگ ثابت minibank:v1، imagePullPolicy: IfNotPresent و kind load docker-image minibank:v1 --name exam.

    (۲) readiness با کد ۴۰۴: مسیر readiness اشتباه است (مثلاً /ready به‌جای /readyz). برنامه برای آن مسیر 404 می‌دهد، readiness هرگز سبز نمی‌شود و pod جدید 0/1 می‌ماند. در rolling update، podهای قدیمی همچنان سرویس می‌دهند و rollout گیر می‌کند. تشخیص از بخش Events در kubectl describe pod. راه حل: اصلاح مسیر در YAML و kubectl apply -f k8s/، یا kubectl rollout undo deploy/<app>.

    (۳) set env و envFrom: kubectl set env یک ورودی صریح env به کانتینر Deployment اضافه می‌کند. متغیر صریح در env بر کلید هم‌نام در envFrom (ConfigMap) غلبه دارد، پس ConfigMap درست است ولی اثری ندارد. kubectl apply هم فقط فیلدهایی را حذف می‌کند که خودش قبلاً گذاشته (در annotation به نام last-applied)؛ متغیری که با set env اضافه شده در فایل ما نبوده، پس apply به آن دست نمی‌زند. راه حل:

    kubectl -n snaplink set env deploy/snaplink REDIS_ADDR-    # خط تیره در آخر = حذف متغیر
# یا
kubectl -n snaplink rollout undo deploy/snaplink
# بررسی
kubectl -n snaplink set env deploy/snaplink --list

kubectl -n <ns> describe pod <name>          # بخش Events
kubectl -n <ns> logs deploy/<app>            # برای pod کرش‌کرده: --previous
kubectl -n <ns> get events --sort-by=.lastTimestamp
